4. ENDPOINTS DA API

Os principais endpoints organizados e implementados foram:

- GET /health: verifica o funcionamento do serviço Backend;
- GET /available-times: consulta os períodos e horários disponíveis para previsões;
- GET /weather-inputs: recupera as informações meteorológicas utilizadas pelo modelo;
- POST /internal/predict: executa internamente o fluxo de previsão;
- POST /predict: recebe solicitações de previsão e coordena a criação dos resultados;
- GET /predictions: consulta o histórico de previsões, permitindo filtros e paginação;
- DELETE /predictions/<prediction_id>: realiza a exclusão de uma previsão armazenada.

Essas rotas permitem que o Frontend utilize as funcionalidades do sistema sem precisar acessar diretamente o banco de dados ou o modelo de inteligência artificial.

5. INTEGRAÇÃO COM O BANCO DE DADOS

Uma das minhas principais responsabilidades foi implementar a integração entre o Backend e o Supabase.

A comunicação foi realizada por meio da API PostgREST, permitindo consultar os registros meteorológicos armazenados na tabela dataset_weather_goes e realizar operações de persistência na tabela resultados_previsoes_ia.

Para organizar essa comunicação, centralizei as operações no arquivo weather_repository.py, separando o acesso ao banco das responsabilidades dos controllers.

A URL e a chave de acesso ao Supabase foram obtidas por meio das configurações de ambiente do servidor.

Também implementei o mecanismo de idempotência utilizando o cabeçalho Idempotency-Key. Esse recurso permite identificar requisições repetidas e evitar a criação de previsões duplicadas, incluindo o tratamento de possíveis conflitos entre requisições concorrentes.

Outra funcionalidade foi a organização da consulta ao histórico de previsões, utilizando filtros por intervalo de tempo e paginação por cursor para recuperar os registros de maneira progressiva.

6. ORGANIZAÇÃO MVC

Participei da organização do Backend utilizando uma adaptação do padrão MVC para uma API REST.

A estrutura foi dividida em:

- Models (app/models/): responsáveis pelo acesso aos dados e pela comunicação com o Supabase;
- Controllers (app/controllers/): responsáveis por receber requisições HTTP, validar parâmetros e coordenar os serviços;
- Views (app/views/): responsáveis pela preparação e padronização das respostas JSON e dos cursores de paginação;
- Services (app/services/): responsáveis pelas regras de negócio, incluindo disponibilidade dos horários, dados meteorológicos e execução das previsões.

Essa separação permitiu organizar melhor as responsabilidades, reduzir o acoplamento entre os componentes e facilitar a manutenção da aplicação.

7. INTEGRAÇÃO COM OUTROS MÓDULOS

Minha atuação também envolveu a preparação da comunicação entre o Backend e os demais módulos do projeto.

Frontend: organização dos endpoints, parâmetros das requisições e formatos das respostas JSON, permitindo consultar horários, solicitar previsões e acessar o histórico.

Banco de Dados: integração com o Supabase para consultar os dados meteorológicos e persistir os resultados das previsões.

Modelo de IA: organização das rotas responsáveis por encaminhar as solicitações aos serviços de previsão e disponibilizar os resultados processados.

O Backend atua como intermediário entre esses componentes, centralizando a comunicação e o acesso aos dados.

8. FLUXO TÉCNICO DA APLICAÇÃO

O fluxo principal de previsão foi organizado da seguinte maneira:

1. O usuário seleciona um horário no Frontend;
2. O Frontend envia a solicitação ao Backend;
3. O controller recebe e valida os parâmetros;
4. O Backend consulta os dados meteorológicos no Supabase;
5. Os serviços verificam os registros de T e T−1h e preparam as entradas;
6. O serviço de previsão encaminha os dados ao modelo de IA;
7. O modelo retorna a probabilidade estimada de chuva;
8. O Backend valida e organiza o resultado;
9. A previsão é armazenada no Supabase;
10. O resultado é retornado ao Frontend e fica disponível no histórico.

Minhas principais contribuições nesse fluxo envolveram a organização das rotas, a comunicação entre os componentes e a persistência dos dados.

10. DIFICULDADES E SOLUÇÕES

10.1. Dificuldade 1: Integração com o Supabase

Era necessário organizar as consultas e operações de persistência sem misturar o acesso ao banco com a lógica das rotas.

Solução: centralização das operações no weather_repository.py, utilizando a API PostgREST.

10.2. Dificuldade 2: Organização da arquitetura

O desenvolvimento de diferentes funcionalidades poderia concentrar muitas responsabilidades nos mesmos arquivos.

Solução: separação do Backend em controllers, models, views e services, mantendo cada componente responsável por uma parte específica da aplicação.

10.3. Dificuldade 3: Requisições duplicadas

O reenvio de uma solicitação poderia gerar previsões repetidas no banco de dados.

Solução: utilização do cabeçalho Idempotency-Key, com consulta prévia dos registros e tratamento de possíveis conflitos de gravação.

10.4. Dificuldade 4: Integração com o Frontend

A comunicação entre os módulos exigia parâmetros e formatos de resposta padronizados.

Solução: organização dos contratos da API, validação das requisições e padronização das respostas JSON e dos códigos HTTP.
